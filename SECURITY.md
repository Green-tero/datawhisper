## Security Model & Invariants

DataWhisper is designed around a **Zero-Trust SQL Execution Engine**. The primary threat model assumes that:
1. The Language Model (LLM) producing SQL is **untrusted** and potentially vulnerable to prompt injection, hallucinations, or adversarial manipulation.
2. The executing environment must protect the underlying database and host machine even if an adversarial prompt succeeds at convincing the model to write malicious SQL.

### Core Invariants:

1. **AST Sandbox Isolation:** All SQL generated by agents or submitted via CLI commands is parsed and validated by an AST-level sandbox using `sqlglot`. We reject multiple statements, comments (`--`, `/* */`), dialect escape hatches, filesystem access functions (`read_csv`, `read_parquet`, `pg_read_file`), and unclassified nodes.
2. **Deterministic Execution:** The engine defaults to deterministic heuristic validation and execution. Network calls to decision engines or LLMs are isolated and never run raw untrusted shell or eval commands.
3. **In-Engine PII Masking:** Sensitive data is redacted (masked, hashed, pseudonymized, or DP-noised) directly within the query engine before data can be serialized or passed to downstream consumers or LLMs.
4. **Execution Timeout & Resource Bounds:** Database backends enforce query timeouts (using native driver interrupts or server-side timeouts) and row limits to prevent denial-of-service via resource exhaustion.

## Reporting a Vulnerability

If you discover a security vulnerability in DataWhisper, please report it privately:

- **Do NOT** open a public issue on GitHub.
- Submit a report via [GitHub Private Vulnerability Reporting](https://github.com/Green-tero/datawhisper/security/advisories/new) or contact the project maintainer directly.
- Include a minimal reproducible example (e.g. SQL snippet, prompt, or test script).
- You will receive an initial response within 48 hours, followed by a patch and security advisory once verified.
